No separate operational upload interface was observed in those event tabs; no Base44 records or files were changed/imported.

## Tasks and staff workflow
Task supports title, description, active assignee, optional Event, calendar due date, Low/Normal/High priority, To Do/In Progress/Completed/Cancelled status, creator/timestamps and completion actor/time. Central Operations and Event Detail query the same records. Event-created tasks bind the event server-side, including if a submitted event field is omitted/tampered with. Managers create/edit/reassign/change status; standalone tasks need no event. Completed/cancelled records remain. Reopening clears current completion metadata but retains prior completion/actor/time in the audit history.

Task lists include all, own, open, completed and overdue views plus search/status/assignee/event/priority filters and pagination. Overdue means an open task due before today's configured local calendar date; due dates are dates, not timezone-specific instants. General staff see only tasks assigned to their active linked profile and cannot change manager-controlled fields. Staff may mark To Do/In Progress tasks In Progress or Completed, never cancel/reopen/reassign. Staff task queries hide Draft-event tasks. Archived event operations are read-only; event lifecycle changes do not silently cancel standalone or other task records.

## Notes and privacy
Notes retain Event, content, original author/creation time, editor/update time, visibility and archival timestamp. Chronological oldest-first pages show author/time and correction metadata. Managers correct/archive; active confirmed event staff can add staff-visible notes and edit their own staff-visible notes. They cannot access manager-only notes or edit another author's note. Archived notes remain visible to managers and excluded from staff lists. Prior content and visibility are retained through existing AuditLog snapshots. Content is escaped on render. No discussion threads, messaging or notification backend.

General event operations access requires either the relevant management permission plus events.view_event, or an active linked profile with a confirmed assignment to that non-Draft/non-Cancelled/non-Archived event. Staff see only staff-visible active documents/notes and their own tasks. Scheduling/task assignment does not grant participant records or other staff's private information.

## Operational documents and storage boundary
EventDocument stores event, title/description, sanitized original filename, MIME type, size, SHA-256, private storage key, uploader/time, visibility, synthetic marker and archival metadata. It is separate from ParticipantDocument; no real participant files are accessed or modified. Archive retains metadata/bytes/audits; no history is hard-deleted.

No durable operational storage is currently configured. Real uploads are disabled server-side and not offered as a working preview control. Render's ephemeral filesystem is not used for operational uploads. On development/gated preview only, authorized managers can explicitly create fixed, visibly SYNTHETIC PDFs to demonstrate permissions, download metadata and archival. The PDF contains no real event instructions or personal data, is generated on demand and requires no uploaded-file persistence. This is explicitly a demonstration, not a real document-upload workflow.

The actual upload adapter and form are implemented and tested against isolated private storage. Future activation requires an explicitly configured private durable root (OPERATIONAL_DOCUMENT_ROOT) or existing Django storage alias (OPERATIONAL_DOCUMENT_STORAGE_ALIAS), plus OPERATIONAL_DOCUMENT_STORAGE_DURABLE=True after durability is verified. This task does not enable those settings, add a provider or change Render configuration. Local private storage reuses PrivateParticipantDocumentStorage with a separate root; storage keys use operational-events/<Event UUID>/<random UUID> rather than user filenames. No public URLs are generated.

Uploads accept nonempty PDF, PNG or JPEG up to 10 MB by default. Existing extension/signature checks are followed by full PDF/image parsing; encrypted/unreadable PDFs, malformed images, paths/control characters and invalid sizes are rejected. Downloads recheck authorization, archival visibility, byte size and SHA-256, force attachment/octet-stream, nosniff, sandbox CSP and private no-store caching. Missing/corrupt bytes return an unavailable response while retaining metadata. A failed database/audit upload cleans up newly created bytes. Retention, backup, scanning and the durable storage service require an explicitly approved deployment configuration before real operational files are accepted.

## Permissions, auditing and integration
Custom operations.manage_tasks, manage_event_notes and manage_event_documents permissions each require events.view_event for management. No migration auto-grants access. Existing Django user/group administration controls manager grants. General staff's narrow own-task and confirmed-event access is service-enforced. All writes are POST/CSRF-protected with atomic transactions and record revision checks. Event/Task/profile locks guard task assignment/status races. Creation, reassignment, status/completion, note edits/archive and document upload/download/archive use existing audit services.

Operations exposes Tasks, My Tasks and Event notes/documents alongside existing staff tools. Event Overview and Staffing link to the three new operational sections; confirmed staff have corresponding safe links from their event summary. Existing Event Overview, Staffing, Results, Registrations and management actions are preserved. Six primary sidebar sections, permission visibility and Settings gear remain. Scoped operations CSS reuses existing fonts/tokens/cards; mobile task-view links remain available. No Home, Participants, public registration, kiosk, simulator, global foundation or offline wire-format redesign. Operational tasks/notes/documents are excluded from the existing registration offline contract.
