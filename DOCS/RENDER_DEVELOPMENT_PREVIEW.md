# Built to Work Render Development Preview

## Purpose and status

This configuration prepares the Django application for a private, browser-based development preview at a permanent Render URL. It is not production approval. No Render service, database, or Git branch has been created by this change.

Use only synthetic development data. Do not import real participant records or legal documents. The preview is not a trailer server and does not run simulator ingestion, trailer synchronization, background delivery workers, or real email/SMS providers.

## Deployment configuration

The repository includes a Render Blueprint in render.yaml for a web service named btw-preview, a separate managed PostgreSQL database, and a private persistent disk. The web service watches the dedicated render-preview branch and deploys commits automatically. The Blueprint is declarative configuration only; an owner must connect the repository and apply it in Render to create resources.

The web service uses:

- Python 3.14.3, pinned in .python-version to match the current project runtime.
- Build command: ./build.sh (install requirements and collect static files).
- Pre-deploy command: python manage.py migrate --noinput (apply migrations to the preview database before release).
- Start command: gunicorn config.wsgi:application --bind 0.0.0.0:$PORT --workers 1 --threads 2 --timeout 120.
- Health check: /health/. It returns only {"status":"ok"}; the preview gate intentionally permits this path for Render probes.
- WhiteNoise with compressed manifest storage for CSS, JavaScript, fonts, and official logos collected under STATIC_ROOT. No public media route is added.

The minimum suggested web plan is Render's 0.5c-512mb single-instance plan, with one Gunicorn worker and two request threads. The Blueprint uses a 1g PostgreSQL plan. Increase these only if observed memory, load, or database usage requires it. The web service needs a paid plan to attach a persistent disk; the attached disk also means this preview should stay at one instance.

## Required Render environment

The Blueprint supplies these values or prompts the owner to enter secrets in Render:

- DJANGO_SETTINGS_MODULE=config.settings.production.
- SECRET_KEY is generated by Render; never copy it into Git or documentation.
- DATABASE_URL is linked to the separate btw-preview-db database. Django uses TLS-required PostgreSQL connections when this URL is present. Existing DB_ENGINE / DB_* settings remain available for local and existing environments when DATABASE_URL is absent.
- ALLOWED_HOSTS=btw-preview.onrender.com and CSRF_TRUSTED_ORIGINS=https://btw-preview.onrender.com. If Render assigns a different generated hostname, update both to that exact hostname before use.
- BTW_PREVIEW_GATE_ENABLED=true, plus a private, owner-chosen BTW_PREVIEW_GATE_USERNAME and BTW_PREVIEW_GATE_PASSWORD. Render must prompt for these secret values. The application fails closed if the gate is enabled without both values.
- PRIVATE_DOCUMENT_ROOT=/var/data/participant_documents, PRIVATE_CONSENT_ROOT=/var/data/consent_documents, and PRIVATE_HISTORICAL_ROOT=/var/data/historical_imports, all located on the mounted disk.
- EMAIL_BACKEND=django.core.mail.backends.locmem.EmailBackend. No delivery worker is defined. Do not add real provider credentials to this preview.

Store generated secrets only in Render's environment settings. Keep separate credentials for the preview and production.

## Access and privacy safeguards

The opt-in preview middleware requires HTTP Basic authentication for the entire site, including public event registration, APIs, and private-document endpoints. Browser access therefore requires two layers where appropriate: the preview gate, then the normal BTW staff sign-in. The gate does not change Django permissions or replace application authentication. HTTPS at Render protects the Basic credentials in transit. Only /health/ is exempt for the platform health probe; it reveals no participant or configuration data.

Production continues to require its existing Django login and permissions. The preview gate defaults off unless explicitly enabled by BTW_PREVIEW_GATE_ENABLED. Do not disable the gate on the public preview.

Participant documents, consent files, and historical import files use private storage roots on the attached disk. They are not served by WhiteNoise or a public media URL; reads still go through authorized application views. A persistent disk is not an encrypted document vault or backup. Limit Render access, use synthetic files, monitor disk capacity, and separately define backups before keeping important data there. Disk data is tied to the service and mount; restoring it to a replacement service requires an explicit recovery plan.

The preview uses a separate empty database. Do not copy the production database. Create its initial Django administrator through the Render service Shell with python manage.py createsuperuser. Do not put administrator passwords into source control or the Blueprint.

## First setup

1. Review and approve the current application changes for preview use.
2. Create render-preview from the approved Build 8 review checkpoint. This task intentionally does not create or push that branch.
3. In Render, connect zeke-chapman-btw/built-to-work and apply the repository Blueprint. Confirm the service name btw-preview, branch, PostgreSQL database, and disk before creating resources.
4. Enter a unique preview-gate username/password in the private Render environment prompts. Confirm that the generated service hostname exactly matches ALLOWED_HOSTS and CSRF_TRUSTED_ORIGINS.
5. Wait for build, static collection, migration, and health checks to pass. If Render provides a different hostname, update both host settings and redeploy.
6. In Render Shell, create a development-only Django superuser. Open the stable HTTPS https://btw-preview.onrender.com/admin/login/ URL; satisfy the browser's preview-gate prompt first, then sign into Django. The BTW operational portal is /internal/.
7. Use only synthetic participants and documents. Confirm public registration is still behind the preview gate and private-document links still require staff authorization.

## Repeated visual-review workflow

Work can happen in Codespaces or desktop VS Code; the running preview is independent of either editor. Develop and test changes on the normal work branch. When a change is ready for owner review, publish the approved review commit to render-preview. Render automatically deploys that branch. The owner revisits the same permanent https://btw-preview.onrender.com bookmark after the deployment succeeds. A preview deployment is not approval to merge or deploy to production. Keep production release and approval on its separate process.

## Operational limitations

- The disk-backed preview runs one web instance; attached disks limit scaling and deployment availability features. Budget for the paid web plan, PostgreSQL, and persistent disk.
- Render's filesystem outside the mounted disk is temporary. Static output is rebuilt on deploy. All sensitive uploaded-file paths must remain under the mounted private roots.
- No background workers, simulator services, trailer sync commands, scheduled jobs, real email, or SMS providers are configured here. Do not start those services in Render.
- This preparation does not provide production data migration, backup/restore operations, malware scanning, or production readiness certification.
- Migrations run as a Render pre-deploy step against the preview database; review future migration behavior before publishing each update.
- Keep the preview's public registrations and storage gate enabled even when testing public-facing pages.
