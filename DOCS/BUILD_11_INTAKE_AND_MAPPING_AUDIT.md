## Configuration and publishing infrastructure

- RegistrationForm owns RegistrationQuestion records and immutable RegistrationFormVersion snapshots. Standard-form initialization supplies defaults; protected question structures cannot be changed in the staff editor. Administrators may edit question wording/help/options/visibility/requiredness/active status/order where permitted, add custom questions, preview versions and publish a new snapshot.
- Staff builder routes are `staff/registration-forms/`, `questions/add/`, `questions/<id>/`, `preview/`, `publish/`. Current implementation requires a superuser, even though some navigation metadata refers to a registration-form permission.
- Publication retires the previous published version and stores active question definitions, labels, options, visibility rules and order in snapshot JSON. Current forms render that snapshot. A later label change does not rewrite earlier submission answers.
- EventRegistrationQuestion and EventGroup are separate event configuration. Online rendering stores event-question definitions, answers and group reference in answer_snapshot; event answers also enter EventRegistration.custom_answers. Offline rendering uses the event question configuration.
- ConsentDocumentVersion and ConsentAcceptance are separate, versioned legal records. Approved text/version/hash is referenced; pending/unapproved legal text blocks relevant registration. This audit does not change consent.
- No general arbitrary intake-to-Participant field-mapping editor was found. Question canonical keys plus explicit code assignments supply profile mapping. Qualification mappings are a distinct, already implemented engine.

## Existing qualification mapping engine

`apps/participants/qualification_models.py` defines controlled categories/catalog entries, exact-choice and custom-text mappings. `qualification_admin.py` provides permission-checked, audited configuration. Only active published mappings for the submission's form and active matching questions apply. `qualification_services.process_registration_submission` snapshots answer/mapping provenance and uses a unique submission/question/answer hash for retries; it does not update earlier derived claims.

`apps/participants/apps.py` loads `qualification_signals.py`. A submitted new RegistrationSubmission or transition to submitted invokes the existing mapping service. The service uses current active/published mapping configuration and current question state for a historical submission's form, rather than a separately frozen mapping revision embedded in the published form version. This distinction matters before approving any historical replay.

Online submission answers are flat canonical-key values. Offline submission answers store dict(data), with event-specific answers nested under 'answers'. Therefore existing qualification mappings may work for matching top-level offline keys, but a mapping expecting an event-specific key at the top level does not automatically find the nested answer. This audit does not flatten or remap it.

## Offline synchronization and integrity

- Local registration retains one stable identity UUID, global registration UUID, QR token/ticket number, form/consent references, source payload, original local IDs and a durable outbox.
- Central registration import validates authorized event, stable identifiers, installed form version and consent version/hash, ticket formatting and timestamps. It retains the source payload and local source IDs; central integer submission IDs may differ. Existing identity contact ambiguity uses the reconciliation/review workflow; there is no new contact-based auto-merge.
- Central-to-trailer downsync includes published form snapshots, event configuration/questions, participant identity/contact/location/DOB/life-stage fields, online/public event registrations, submission answers/snapshots, consent and tickets. It does not replicate the full ParticipantCareerProfile or Build 11 staff notes/work history/acquisition extension as a comprehensive participant mirror.
- Central import creates a new participant's mapped identity/contact/location fields but does not construct a complete career profile from every stored answer. Existing central identity data is not overwritten from trailer answers.
- Existing qualification post-save processing can run as submissions are imported, subject to installed central mappings and answer shape. The existence of this hook does not prove matching configuration exists on both instances.
- Build 11 leaves intake forms, mapping engine, published mapping configuration and offline protocols unchanged. Original acquisition can be entered/corrected with evidence in the staff workspace; missing origins stay unknown. Automatic original-source capture/transport for all intake families is **not implemented** and requires explicit follow-up review. This is separate from the working manual acquisition record, filters and charts.
- No physical trailer, scanner, kiosk hardware or end-to-end disconnected deployment was tested by reading this code. Automated regression results are recorded separately.

## Gaps for owner review before final Build 11 acceptance

1. Approve a field-by-field mapping contract: general versus construction-specific experience; career/skills text versus catalog claims; explicit employment preference; geographic preferences; travel unknown/no; structured education and work history.
2. Decide whether and how address/industry/travel-distance/conditional answers should appear in the current profile. Do not automatically reinterpret existing answers.
3. Decide trusted returning-person intake behavior. Independent anonymous online registrations currently create separate records; request-key retry safety is not person-level deduplication. Contact matches alone are not safe identity proof.
4. Decide automatic original-source capture and offline transport, including public event links versus physical event intake. A reference to an event must not be mistaken for attendance or original Event acquisition without an approved rule.
5. Approve mapping versioning and historical replay policy before changing mappings or backfilling old submissions. Preserve self-reported/verified separation and never overwrite reviewed credentials.
6. Review offline nested answer shape, standard-form/question parity and required validation; agree which profile/qualification data should be synchronized and who owns conflict resolution.
7. Inspect deployed form versions and published mappings in an authorized configuration review before promising specific live form fields. This audit did not enumerate operational configuration rows.
8. Decide staff profile visibility of raw intake snapshots, avoiding unnecessary DOB/address exposure. Current workspace shows references; original snapshots remain in existing authorized administrative workflows.

9. Review canonical field validation as well as mapping. SnapshotRegistrationForm renders generic short-text questions as CharField(max_length=500), including the default contact-email/name/phone keys; it does not automatically inherit EmailField validation or each Participant column's shorter length. The online view creates Participant directly without full_clean. Invalid email formats or overlong canonical values therefore need a separate validation review, particularly against PostgreSQL column limits. This is an existing source-level finding; no validator or intake change was implemented.

No new intake mapping, importer, backfill, identity merge or form-builder functionality is authorized by this audit. These gaps remain review items, not silently completed features.
